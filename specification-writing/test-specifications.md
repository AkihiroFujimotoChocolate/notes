# テスト仕様書

## 1. 目的と対象

採用済みの仕様に基づいて、試験担当者が操作、観測、比較、合否を決められるようにする。

| 種類 | 確認内容 |
|---|---|
| 外部テスト | 入力に対する外部から観測できる要求・応答・副作用 |
| 内部テスト | 内部契約で定めた宣言、依存、責務、構成、直接呼出しの結果 |

外部テストは可能な限り対象の通常経路を使い、外部依存を適切な境界で差し替える。内部の構造や処理の確認では、直接呼出し、実際のDI構成、コンパイルされた依存関係の検査などを選択する。外部SDK自体の振る舞いと自作コードの契約を区別し、SDK代役と実SDK・エミュレーターの確認範囲を示す。

## 2. 推奨章構成

| 章 | 内容 |
|---|---|
| 1. 対象・適用範囲 | 試験対象、適用版、観測境界。 小節：対象と目的、試験対象の境界。 |
| 2. 共通条件 | 共通の準備、操作、判定、診断。 小節：試験環境と共通設定、入力と代役の条件・期待結果、観測と判定、共通実行手順、診断記録と再現方法。 |
| 3. テストケース | ケース一覧と固有の条件。 |
| 4. テストコードの配置・対応 | ケースとコード配置の対応。 |
| 5. 参照資料 | 根拠仕様と確認版。 |

2章の小節は次の構成を推奨する。第三階層には対象ごとの見出しを置く。

| 節 | 主な下位見出し・内容 |
|---|---|
| 2.1 試験環境と共通設定 | 試験環境、共通設定、試験側の時間制限 |
| 2.2 入力と代役の条件・期待結果 | 生成値、入力、外部依存の応答、内部境界の代役 |
| 2.3 観測と判定 | 要求の捕捉、JSON・引数・件数の比較、内部宣言 |
| 2.4 共通実行手順 | 準備、操作、観測、終了・後始末 |
| 2.5 診断記録と再現方法 | 実行前の記録、固定値での再現方法 |

外部・内部で共通する見出しと表現を揃え、異なる観測方法は対象に合わせる。外部テストと内部テストを一つの文書に記載する場合は共通条件を共有し、ケースIDを外部・内部で区別する。

## 3. 試験環境と観測

外部HTTP APIの場合、通常のアプリケーション起動経路と本番のサービス登録を使い、設定・外向き通信を試験用に変更する方法がある。例えばASP.NET Coreではテストホストを利用する。試験ごとのホスト、記録、設定を独立させる。外部仕様の確認に必要な経路が代役で隠れないようにする。

| 観測対象 | 比較方法 |
|---|---|
| HTTP要求 | メソッド、送信先、必要なヘッダー |
| JSON本文 | デコード後の型・値・件数・必須項目。順序やエスケープ表現は契約で指定した場合に比較 |
| ID | 入力の値、または生成された値との対応 |
| 通信回数 | 観測対象と終了条件を定めた上で件数を比較 |
| 複数候補から選択 | 規定の候補のいずれかと一致。分布が契約の場合は別途判定方法を定める |

非同期処理では、代役が要求到達を通知し、試験側が応答・取消を制御する方法を利用できる。固定時間の待機だけで「送信0件」を判断せず、完了・停止・処理境界などの観測可能な条件と対応付ける。試験側の上限時間と本体のタイムアウト設定を区別する。

## 4. ケースの書き方

3章の冒頭に一覧を置く。

| ケースID | 確認目的 | 条件数 | 根拠条項 |
|---|---|---:|---|
| 外部-01 | 正常登録 | 1 | 外部仕様3.4 |
| 外部-02 | 入力エラー | 1 | 外部仕様3.3 |

各ケースは準備、操作、観測、期待結果を記載し、差分条件は表にする。一つのケースに複数の処理や確認段階がある場合は第三階層の見出しで区分する。

| 条件ID | 準備・操作 | 期待結果・合否条件 |
|---|---|---|
| 外部-02-01 | titleを空文字として送信 | HTTP 400、保存への要求0件（観測境界で確認） |

共通設定をケース固有の設定で上書きする場合はその優先関係を書く。結果だけでなく、判定に使う観測先・取得時点・比較値を定める。

### 4.1 条件と趣旨

全条件に共通する準備・操作・期待結果を一箇所にまとめる。差分となる値・条件は表に記載する。複数の設定の組合せが確認対象なら、各設定キーを列にする。複数の処理を観測するなら、観測先ごとの結果を列にできる。

確認目的だけではテストの趣旨が読み取れない場合は、手順・条件・期待結果への補足と分かる形で趣旨を記載する。補足を新たな合否条件にしない。対応するテストコードに趣旨の英文をコメントとして記載する方法も選べる。

試験の共通手順は番号付きリストで記載する。個々の接続先に対する要求の判定は対象ごとの第三階層で整理し、送信先、HTTPヘッダー、JSON本文、HTTP応答をそれぞれ適した表にする。詳細は[テスト仕様の記述例](writing-examples/test-specifications.md)を参照する。

## 5. 入力と再現性

固定の代表値、境界値、既知不具合の回帰値、生成値を目的に応じて選ぶ。生成するID等は形式・長さ・生成時点を定め、実際に使った入力・設定・代役の応答を記録する。試験側で生成する値は、外部契約が許す範囲で用途別の接頭辞を使うと記録から役割を読み取れる。本体で採番する識別子とは区別する。再現時には記録された固定値を入力できる経路を用意する。生成器・期待値生成の複雑さやCIでの不安定さも考慮する。ランダム試験を必須にするか探索用にするかはプロジェクトで決める。

## 6. 独立性

テスト仕様の期待結果は本体コードの実装結果から導かず、採用済み仕様から作る。本体のserializer・mapperなどと同じ計算で期待値を作ると共通の誤りを見逃す可能性がある。独立性を強く求める開発では、試験担当者が本体ソースを参照しない形でテスト仕様・コードを作成し、本体担当にもテストコードを先に渡さない運用を選択できる。採用時は参照権限、公開履歴、作業ブランチを確認し、参照範囲を作業条件に明記する。

### 6.1 テストコードの書き方

既存テストコードを参考にする場合の推奨手順：

1. テスト仕様書で参照した資料に対応する既存コードを確認し、目的・試験方式に近いコピー元を選ぶ。
2. 選んだコードをコピーし、確定したテスト仕様に必要な差分を加える。
3. コピー元で判断できない書き方を使用技術の公式サンプルで補う。
4. 公式サンプルとコピー元で書き方が異なる場合は、プロジェクトの方針と整合する既存の書き方を優先する。

既存コードの変更では現行の変更対象を確認する。同じ検証は同じコードで表現し、既存の補助部品を活用する。各ケースから準備・操作・判定が追える構造にする。新規の補助部品が必要なら、用途・必要性・追加案を作成前に確認する。既存試験の目的と保証を維持する。

仕様で保証していないUUIDの版・表記、JSONのプロパティ順・エスケープ、ログの文言、任意の内部構成を合否条件に追加しない。
