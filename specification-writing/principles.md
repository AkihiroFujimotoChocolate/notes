# 基本原則・文書構成

## 1. 目的

仕様書は実装に必要な契約・処理・構造を定める。テスト仕様書は採用済みの仕様から試験の操作、観測、合否を決める。担当者が仕様書を読んで同じ判断に到達できる記述を目指す。

## 2. 文書の役割

| 資料 | 記載内容 |
|---|---|
| 外部仕様 | 利用者や他の構成要素から観測できる入出力、条件、結果、設定 |
| 内部仕様 | 必要な責務、依存、型、境界、構成、差替え |
| テスト仕様 | 準備、操作、観測、比較、期待結果、診断、再現 |
| 仕様・テスト対応表 | 条項と確認方法の関係、未確認範囲 |
| 設計判断記録・レビュー記録 | 理由、代替案、却下理由、未決事項、過去の経緯、指摘 |
| 作業記録 | 実行環境、実行結果、証跡、進捗 |

仕様本文に実装・判定に必要な条件を書く。レビュー担当への注意、将来の構想、採用しなかった案は適切な記録へ置く。動作や安全性を決める制約は仕様に記載する。例：権限がない要求は拒否する。

## 3. 文書の分割・統合

| 構成 | 適する場合 |
|---|---|
| 外部仕様のみ | 内部構造を実装担当者に委ねるAPI、ライブラリ |
| 内部仕様のみ | 外部契約が既存資料で確定した内部改修 |
| 外部・内部を統合 | 一緒に保守する小規模サービスや機能 |
| 外部・内部を分離 | 契約の読者や変更頻度が異なる、複数版・担当分離 |
| 章構成を簡略化 | 小さなツールなど、少数の入出力・処理・異常・設定で十分な場合 |

外部テストと内部テストも同じ考え方で分離・統合を選ぶ。単純な機能に全章を強制する必要はない。共通テンプレートを採用する文書群では章・節番号と役割を維持し、項目がない場合は「該当なし」とする。仕様を定めていない場合は「未規定」と記す。テンプレートの変更は文書群全体の比較やリンクへの影響を確認する。

## 4. 具体性と範囲

- 主体、入力、条件、動作、結果を特定する。一般的な技術用語を使い、独自の用語は必要な場合だけ定義する。
- 固定値、設定値、他の要求・応答から得る値、生成値を明記する。
- 同じ契約の記載は一箇所にまとめ、他の箇所は節を参照する。
- 未規定の事項は既定の契約・変更範囲に沿って変更しやすい実装を選び、判断を記録する。新しい外部契約・権限・安全性に関わる判断は承認を得る。仕様と試験の対象にする際は契約を確定する。
- 規定の追加・削除は実装、試験、互換性への影響を調べる。

## 5. 文章の精度

仕様の文章は実際に必要なロジックを表す。例えば、入力ごとにIDを発行する契約なら「入力本文が同じ場合も異なるIDを発行する」より「入力ごとにIDを発行する」と記載する。本文の一致を調べる分岐を仕様から読み取らせないためである。

処理を終了する分岐が定まるなら、その分岐と終了を記載する。観測する要求件数はテスト仕様に記載する。件数そのものが外部契約である場合は仕様に残す。

- 名称は対象の契約・役割を表す。接続先の実装が暫定的でも、契約が同じならその事情を名称に持ち込まない。
- 現行の適用範囲で使用しない機能・基盤・設定は将来計画に記載する。
- 他の箇所の規定から動作が特定できるなら、重複する禁止・注意文を追加しない。
- 一般的な型・階層表記で判断できる情報を繰り返さない。
- 「要求」などの語だけでは対象を特定できない場合は、誰から誰への何の要求か示す。
- 規定内容に合わない既存文は、否定文や補足を積み重ねず、対象の仕様から書き直す。

## 6. 自己点検

実装担当者と試験担当者が互いのコードを見ずに仕様を読んだとき、同じ入力・結果・必要な境界を選べるか確認する。不一致が生じるなら、対象の条件または値の取得元、比較方法、責務を具体化する。
