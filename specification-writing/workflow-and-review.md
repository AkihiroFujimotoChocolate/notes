# 作成・レビュー・改訂

## 1. 作成順序

1. 対象範囲、既存契約、採用済み判断を確認する。既存の同種仕様書は新しいものから確認し、共通する章・表現を揃える。公式資料や参照実装を選び、使用箇所・参照版・理由を記録する。
2. 外部仕様と必要な内部仕様を作成する。未決事項は仕様の確定範囲と区別して扱う。
3. 仕様をレビューし、採用内容を確定する。
4. 確定仕様からテスト仕様・対応表を作成してレビューする。
5. テストコードを作成・点検し、本体実装の指示を仕様と既存コードとの差分から具体化する。
6. 本体実装・テストを必要な順序で結合し、ビルド、試験、レビュー、実際の配置環境の確認を行う。

独立性を重視する場合、本体実装担当には仕様・必要な作業条件を渡し、試験担当には確定仕様を渡す。互いのコードを先に参照しない。結合前に全テストが成功することは前提にしない。既存動作の調査が必要なら仕様整備側で行い、必要な契約だけを採用する。

## 2. 実装指示

変更対象、作業開始点、追加・変更する動作・型・設定・受渡し、成果物を具体化する。現在のコードに存在する挙動と新しい要求を区別する。レビュー上の注意や未採用案を実装指示へ混在させない。指示外の実装があった場合、仕様違反や責務の破壊など実際の影響を評価する。

## 3. レビュー観点

| 対象 | 確認すること |
|---|---|
| 外部仕様 | 条件・主体・型・値・応答・順序・例外が決まるか |
| 内部仕様 | 責務・依存・必要な宣言・生存期間・差替えが特定できるか |
| テスト仕様 | 準備・操作・観測・期待結果・終了が特定できるか |
| 対応表 | 各条項に必要な確認が対応し、未対応範囲が分かるか |
| コード | 指定仕様との整合、構文、名前解決、共通部分、診断、変更の影響 |
| 文書共通 | 表・見出し・図・リンク、重複、矛盾、未決事項の混入 |

レビューの指摘は対象、根拠、修正が必要な理由を記録する。単なる記述整理と仕様変更を区別する。判定に必要な条件が欠けている場合は、仕様の追加案として検討する。

## 4. 改訂の手順

変更案が確定したら、既存正本を基に反映後の完成品を作り、採用差分と必要な機械的変更だけが入ったかを照合する。続けて完成品を仕様・記述ルール・関連文書に照らして点検し、訂正が必要なら判断を記録する。正式反映後は完成品と一致するか、相対リンクや参照版が正しいかを確認する。不要な作業用文書は履歴を参照できるように整理する。

テスト仕様の改訂では、旧ケースの目的・保証・診断を確認し、ケース数や期待値の増減・レビューへの移管の根拠を残す。

## 5. 版追加と環境変更

新しい契約版を追加する際、既存版と新しい版で同じ仕様・確認を同じ表現とコードに揃える。版固有の差は対象版に局所化する。既存版に全ての別版の具体型や接続先を列挙すると、版追加のたびに既存文書や試験の変更が生じる。必要な選択規則・共通境界を適切な抽象度で示す。共通部分の抽出は目的と保守への影響に照らして選ぶ。

SDK・ランタイム・ターゲットフレームワークの変更は次の観点を作業計画に含める。

| 確認対象 | 具体例 |
|---|---|
| SDK・共通設定 | global.json、プロジェクトSDK、共通ビルド設定 |
| 本体 | ターゲットフレームワーク、依存パッケージ |
| テスト | 本体を参照するテストプロジェクトのフレームワーク、テスト用パッケージ |
| 分割作業 | 共通始点、取り込み順、一時的な条件付き設定 |
| CI | 使用SDK、restore・build・testの引数、テスト検出・実行 |
| 実行環境 | コンテナ、ランタイム、配置、起動・スモーク確認 |

静的確認と実際のrestore・build・test・CI・配置確認を区別する。結合時に一時設定の整理と実行結果を確認する。これは環境変更を計画する際の推奨チェックである。

## 6. 記録

採用済み仕様は正本へ、判断理由・比較・変更の経緯は判断記録へ、試験・レビューの実行結果は作業記録へ置く。公開資料は秘密情報や非公開の判断記録を含めず、例は公開可能な値に置き換える。
